# stream-companion

Личный компаньон для стримов на Twitch. Реализовано:

1. **Заказ музыки через чат Twitch** (`!sr <ссылка или название трека>`), с
   проверкой фолловера, валидацией ссылки (YouTube/Spotify/Яндекс Музыка — либо
   текстовым поиском по Spotify, если ссылки нет) и переключением между
   дефолтным плейлистом (Spotify или Яндекс Музыка) и очередью заказов.
2. **Скип трека голосованием** (`!skip`) — работает и для заказов, и для
   треков дефолтного плейлиста: стример скипает сразу (модераторы и заказчик —
   если разрешено настройками), зрители —
   голосованием от числа активных в чате.
3. **Заказ музыки за баллы канала** — отдельный режим вместо команды `!sr`
   (`MUSIC_REQUEST_MODE=points`): те же правила, кроме фолловинга; заказ не
   прошёл — баллы возвращаются (см. "Заказ за баллы канала" ниже).
4. Spotify целиком необязателен — без него приложение просто работает в
   режиме "только YouTube" (см. раздел "Необязательная интеграция" ниже).
5. Яндекс Музыка тоже необязательна: заказы по ссылкам на music.yandex.ru
   принимаются, только если задан `YANDEX_MUSIC_TOKEN` (см. "Яндекс Музыка" ниже).
6. YouTube тоже можно отключить (не задавать `YOUTUBE_API_KEY`), но хотя бы
   один источник заказов должен быть настроен — иначе приложение не стартует
   (см. "Проверка источников заказов при старте" ниже).

## Windows: запуск без консоли (bat-файлы)

В папке с приложением есть готовые `.bat`-файлы — их можно просто открывать
двойным кликом, набирать команды в консоли не нужно (Node.js и `mpv`/`yt-dlp`
всё равно должны быть установлены, см. ниже, но сами команды за тебя
запускают именно эти файлы):

- **`start.bat`** — обычный запуск приложения. При самом первом запуске,
  если `.env` ещё нет, сам создаст его из `.env.example` и откроет в
  Блокноте для заполнения — само приложение при этом ещё не стартует,
  нужно будет запустить `start.bat` ещё раз после того, как `.env` заполнен.
  Окно с логами не закрывается само по себе — заказ музыки печатает
  сообщения прямо туда, а любую ошибку можно спокойно прочитать, окно ждёт
  нажатия клавиши перед закрытием.
- **`setup-0-twitch-broadcaster-id.bat`** — спросит логин канала и покажет
  его числовой id для `TWITCH_BROADCASTER_ID` (нужен `TWITCH_CLIENT_ID`/
  `TWITCH_CLIENT_SECRET` в `.env`, заполненные заранее).
- **`setup-1-twitch-auth.bat`** — одноразовая авторизация Twitch (нужна
  всегда, без неё не будет работать ни чат, ни заказ музыки).
- **`setup-2-spotify-auth.bat`** — одноразовая авторизация Spotify (нужна,
  только если настраиваешь интеграцию со Spotify — см.
  "Необязательные интеграции" ниже).
- **`setup-3-spotify-devices.bat`** — покажет список устройств Spotify
  Connect для `SPOTIFY_DEVICE_NAME` (тоже только для Spotify).
- **`setup-4-twitch-points-auth.bat`** — одноразовая авторизация стримера
  для заказа за баллы канала (нужна, только если `MUSIC_REQUEST_MODE=points`).
- **`setup-5-yandex-music-auth.bat`** — получение токена Яндекс Музыки
  (`YANDEX_MUSIC_TOKEN`), нужно только для заказов и дефолтного плейлиста из
  Яндекс Музыки. Откроет страницу входа Яндекса; после входа скопируй адрес из
  адресной строки браузера и вставь в окно — токен проверится и сам запишется
  в `.env`. Токен живёт около года, потом запусти файл снова.
- **`check-music.bat`** — проверка перед стримом (`npm run check:music`): по
  очереди убеждается, что играет дефолтный плейлист и что реально играют
  заказы по ссылке Spotify, по названию (поиск Spotify), по ссылке YouTube и
  по ссылке Яндекс Музыки. «Играет» проверяется по-настоящему: трек Spotify
  должен появиться на устройстве с растущей позицией, у mpv должен пойти звук.
  Каждый трек звучит несколько секунд, в конце — итог `[ OK ]`/`[FAIL]` по
  каждому пункту. Займёт около минуты. Spotify должен быть открыт, а само
  приложение — закрыто (если оно запущено, проверка откажется стартовать,
  чтобы не перехватить его музыку). Заказы идут в отдельную очередь в памяти,
  база приложения не трогается. Тестовые треки — в начале
  `scripts/music-check.ts` (`CHECK_REQUESTS`), если какой-то пропадёт —
  замени ссылку там.

Цифры в именах файлов — просто рекомендуемый порядок для самого первого
запуска, сами по себе они никак не связаны, каждый можно запускать отдельно
в любой момент. Дальше по тексту команды вида `npm run ...` — это то же
самое, что делают эти `.bat`-файлы, но напрямую в терминале; на Windows
удобнее пользоваться файлами, а команды пригодятся на macOS/Linux или если
уже работаешь в терминале.

## Особенность: без npm-зависимостей в коде приложения

Сам код ничего не устанавливает через `npm install` — используются только
встроенные возможности Node.js 22+: нативная поддержка TypeScript,
`node:sqlite`, `fetch`, `WebSocket`, `process.loadEnvFile()`, `node:test`.
Требуется Node.js **22.6+**. Проверить версию: `node --version`.

Для заказа музыки дополнительно нужны два **системных** (не npm) инструмента:

- **yt-dlp** — сам скачивает аудио заказанного видео и стримит его сырые
  байты в stdout;
- **mpv** — читает эти байты из stdin и просто проигрывает их как локальный
  плеер, никаких собственных сетевых запросов к YouTube не делает.

(Раньше было наоборот — mpv сам резолвил ссылку через встроенный yt-dlp-хук и
скачивал её самостоятельно. Так теперь не делается: YouTube научился в ряде
случаев блокировать именно сетевой запрос mpv/ffmpeg к googlevideo.com (HTTP
403), даже когда та же самая ссылка секунду назад успешно скачивалась через
сам yt-dlp — см. подробности про `HTTP error 403 Forbidden` ниже.)

**Windows:** `winget install -e --id shinchiro.mpv` и `winget install -e --id yt-dlp.yt-dlp`
(либо через Scoop/choco). После установки закрой и заново открой терминал —
PATH обновляется только в новых окнах — и проверь `mpv --version` /
`yt-dlp --version`.

Важно про **обновление yt-dlp**: YouTube меняет формат страниц и правила
доступа очень часто (речь о неделях, не месяцах), и yt-dlp столь же часто
выпускает исправления — но `winget` подтягивает их с задержкой и иногда
путается в версиях (пишет, что обновление есть, хотя ты уже обновился
вручную, или наоборот). Поэтому если заказы с YouTube внезапно перестали
работать — **в первую очередь** обнови yt-dlp напрямую, а не через winget:
```powershell
yt-dlp -U
```
Если это не помогает или `yt-dlp -U` вообще недоступен — скачай последний
`yt-dlp.exe` напрямую со страницы релизов
(https://github.com/yt-dlp/yt-dlp/releases/latest) и either замени им файл,
который сейчас стоит в PATH, либо положи отдельно и укажи путь к нему через
`YTDLP_PATH` в `.env` — это подстрахует от случая, когда на машине по факту
несколько yt-dlp (например, старый от winget и рядом свежий .exe), и mpv
берёт не тот, что ты только что обновил.

**macOS:** `brew install mpv yt-dlp`

**Ubuntu/Debian:** `sudo apt install mpv` для mpv — но пакет `yt-dlp` в репозиториях
apt обычно устаревший (YouTube часто меняет формат страниц, и старый yt-dlp
из-за этого перестаёт работать). Надёжнее поставить и обновлять yt-dlp
отдельно от apt:
```bash
sudo curl -L https://github.com/yt-dlp/yt-dlp/releases/latest/download/yt-dlp -o /usr/local/bin/yt-dlp
sudo chmod a+rx /usr/local/bin/yt-dlp
```
Обновление в будущем — та же команда ещё раз, либо `yt-dlp -U`.

После установки проверь, что обе программы видны в PATH:
```bash
mpv --version
yt-dlp --version
```
Если `yt-dlp --version` не находится — mpv не сможет проигрывать YouTube-заказы,
даже если сам mpv установлен и работает.

**Если YouTube-заказ падает с ошибкой вида `Процесс плеера "mpv" завершился с
кодом 2`** — в логе теперь дополнительно печатается реальный вывод mpv/yt-dlp
(до этого он подавлялся флагом `--really-quiet`, и был виден только голый код
выхода). Смотри, что именно написано в выводе:

- **mpv вообще не понимает YouTube-ссылки / незнакомая ошибка** — почти
  всегда дело в версии yt-dlp. Обнови её способом из раздела про установку
  выше (`yt-dlp -U`, при необходимости — свежий `.exe` + `YTDLP_PATH`) и
  попробуй заказ ещё раз.
- **`Sign in to confirm you're not a bot`** — YouTube требует подтверждения,
  что запрос не от бота. Приложение по умолчанию уже пытается это обойти
  через `YOUTUBE_PLAYER_CLIENT` (см. `.env.example`). Если не помогает —
  добавь `YOUTUBE_COOKIES_FROM_BROWSER=firefox` (на Windows именно Firefox
  надёжнее всего для этого — не нужно закрывать браузер и нет проблем с
  шифрованием куки Chrome).
- **`The page needs to be reloaded`** — отдельная, тоже известная ошибка:
  так YouTube отвечает, когда конкретное сочетание "клиента" (см.
  `YOUTUBE_PLAYER_CLIENT`) и версии yt-dlp у него сейчас не в почёте. Сначала
  обнови yt-dlp (см. выше) — иногда этого достаточно. Если нет — попробуй
  другое значение `YOUTUBE_PLAYER_CLIENT`, например `web,web_safari,web_embedded`.
  Важно: если параллельно задан `YOUTUBE_COOKIES_FROM_BROWSER`/`_FILE`,
  клиент `tv` сам yt-dlp незаметно подменяет на `tv_downgraded` — если у
  тебя настроены и куки, и `player_client=tv`, и именно эта ошибка — попробуй
  временно убрать куки или сменить клиента.
- **`HTTP error 403 Forbidden`** — раньше (когда именно mpv/ffmpeg сам
  скачивал ссылку на googlevideo.com) эта ошибка означала, что скачивающий
  запрос попал под анти-бот блокировку YouTube — сама ссылка при этом почти
  всегда оставалась рабочей (та же ссылка секунду спустя открывалась через
  yt-dlp или даже обычный curl), просто блокировался именно сетевой клиент
  mpv/ffmpeg. Никакие `YOUTUBE_PLAYER_CLIENT`/куки/`YOUTUBE_FORCE_IPV4` это
  не лечили — они влияют только на то, как РЕЗОЛВИТСЯ ссылка, а не на то, кто
  её СКАЧИВАЕТ. Поэтому теперь скачивание аудио целиком делает сам yt-dlp
  (см. "Как играют YouTube-заказы" выше), а mpv — только проигрывает готовые
  байты, и с этой ошибкой сталкиваться не должно. Если она всё равно
  появляется — значит с 403 упал уже сам yt-dlp при скачивании (а не mpv), и
  дело либо в устаревшей версии yt-dlp (`yt-dlp -U`), либо снова в анти-бот
  блокировке — попробуй `YOUTUBE_COOKIES_FROM_BROWSER=firefox`.
- Ошибки выше — это, по сути, текущее состояние "гонки вооружений"
  между YouTube и yt-dlp: то, что работает сегодня, через месяц может
  перестать, и наоборот. Если ничего из вышеперечисленного не помогло — стоит
  заглянуть в открытые issue на https://github.com/yt-dlp/yt-dlp/issues
  (поиск по тексту ошибки) — почти наверняка проблему уже обсуждают и там
  есть актуальный обходной путь.

Spotify-часть очереди (сами заказы с open.spotify.com) играет через Spotify
Connect API — там ничего локально ставить не нужно, но **обязателен Spotify
Premium**: обычный аккаунт не даёт Web API управлять воспроизведением.

## Необязательная интеграция (Spotify)

Spotify — необязателен, описывается своей группой переменных окружения в
`.env`: `SPOTIFY_CLIENT_ID` + `SPOTIFY_CLIENT_SECRET` + `SPOTIFY_DEFAULT_PLAYLIST_URI`.

Если не заполнена хотя бы одна переменная группы — интеграция отключается,
при старте в лог пишется, каких именно переменных не хватает, остальное
приложение работает как обычно (текстовый поиск трека и ссылки на Spotify
не принимаются, `!sr` отвечает соответствующим сообщением).

## Проверка источников заказов при старте

YouTube (`YOUTUBE_API_KEY`), Spotify (группа выше) и Яндекс Музыка
(`YANDEX_MUSIC_TOKEN`) необязательны по отдельности. При старте приложение
проверяет их по очереди: для каждого источника пишет в лог либо "настроено",
либо каких переменных не хватает (такой источник отключается, ссылки на него
отклоняются). Если не настроен ни один источник — приложение сообщает об этом
и завершает работу.

## Необязательная интеграция (Яндекс Музыка)

Заказы из Яндекс Музыки включаются одной переменной `YANDEX_MUSIC_TOKEN`. Проще
всего получить её через `setup-5-yandex-music-auth.bat` (или `npm run auth:yandex`):
он сам запишет токен в `.env`. Ручной способ описан в `.env.example`. Нужен аккаунт с подпиской Плюс: без неё Яндекс отдаёт только
30-секундные превью.

- Принимаются ссылки `https://music.yandex.ru/album/<id>/track/<id>` и
  `https://music.yandex.ru/track/<id>` (а также домены .com/.by/.kz/.uz).
  Ссылки на альбомы и плейлисты целиком не принимаются.
- Официального API у Яндекс Музыки нет, используется API её собственных
  приложений (`api.music.yandex.net`). Название и исполнителя приложение
  получает через него, прямую ссылку на mp3 тоже, и отдаёт её mpv. Браузер и
  yt-dlp не нужны: экстрактор Яндекс Музыки в yt-dlp сейчас сломан.
- Звук идёт через тот же mpv, что и у YouTube-заказов, с теми же
  `MPV_VOLUME` и `MPV_AUDIO_DEVICE`, так что в OBS он попадает туда же.
- Громкость треков выравнивается под уровень Spotify
  (`YANDEX_LOUDNESS_TARGET_LUFS`, по умолчанию −14 LUFS — как "Обычная"
  громкость в Spotify): Яндекс сам сообщает измеренную громкость каждого
  трека, и mpv получает поправку. Без этого соседние треки могут отличаться
  по громкости на 8–9 дБ. Применённая поправка пишется в лог.
- **Дефолтный плейлист из Яндекс Музыки** — `YANDEX_DEFAULT_PLAYLIST_URL`
  (ссылка из "Поделиться → Скопировать ссылку"), вместо
  `SPOTIFY_DEFAULT_PLAYLIST_URI`. Задать оба нельзя: приложение не стартует.
  Spotify при этом можно оставить для заказов (только `SPOTIFY_CLIENT_ID` и
  `SPOTIFY_CLIENT_SECRET`). Треки плейлиста играет mpv; в остальном он
  работает так же, как дефолтный плейлист Spotify (см. "Как работает заказ
  музыки" ниже).
- **Моя волна вместо плейлиста** — `YANDEX_DEFAULT_PLAYLIST_URL=WAVE`. Треки
  приходят порциями по несколько штук; следующая порция подгружается заранее,
  пока доигрывает предыдущая. Волна получает обратную связь (трек доигран или
  скипнут) и подстраивает следующие треки — только в пределах сессии: волна
  запускается "инкогнито" и не влияет на рекомендации аккаунта. Перемешивание
  (`DEFAULT_PLAYLIST_SHUFFLE`) на волну не действует.
- API неофициальный, Яндекс может его изменить. Если заказы Яндекс Музыки
  перестали играть, смотри ошибку в логе (`[playback] Ошибка воспроизведения заказа`).

## Установка

1. Убедись, что стоит Node.js 22.6+, а также `mpv` и `yt-dlp` (см. выше).
2. Скопируй `.env.example` в `.env`:
   ```bash
   cp .env.example .env
   ```
3. Заполни `.env` — подробные комментарии есть в самом файле, но по шагам:

   **Twitch (общее)**
   - `TWITCH_CLIENT_ID` / `TWITCH_CLIENT_SECRET` — зарегистрировать приложение на
     https://dev.twitch.tv/console/apps. В OAuth Redirect URLs добавь
     `http://localhost:8889/callback`. Важно: именно `localhost`, а не
     `127.0.0.1` — с ним Twitch выдаёт ошибку "URL-адреса должны
     использовать протокол HTTPS" (для http Twitch разрешает только
     буквально `localhost`; у Spotify ниже правило обратное).
   - `TWITCH_BROADCASTER_LOGIN` — логин канала.
   - `TWITCH_BROADCASTER_ID` — узнать после того как заполнишь Client ID/Secret:
     на Windows проще всего `setup-0-twitch-broadcaster-id.bat` (см. выше),
     либо в терминале:
     ```bash
     node scripts/twitch-user-id.ts <TWITCH_BROADCASTER_LOGIN>
     ```

   **Заказ музыки — чат**
   - `TWITCH_CHAT_BOT_USERNAME` — от чьего имени бот пишет в чат. Если это ты
     сам — тот же логин, что и `TWITCH_BROADCASTER_LOGIN`. Если отдельный
     бот-аккаунт — он должен быть модератором канала.
   - `MUSIC_COMMAND` (по умолчанию `!sr`), `MUSIC_MIN_FOLLOWER_DAYS` (по умолчанию `3`).
   - `MUSIC_SKIP_COMMAND` (по умолчанию `!skip`), `MUSIC_SKIP_THRESHOLD_PERCENT`
     (по умолчанию `30`), `MUSIC_MODERATOR_SKIP_REQUESTS` и
     `MUSIC_REQUESTER_SKIP_REQUESTS` (по умолчанию `false`) —
     скип текущего заказа, см. "Как работает скип" ниже.

   **Заказ музыки — YouTube**
   - `YOUTUBE_API_KEY` — API-ключ с включённым YouTube Data API v3:
     https://console.cloud.google.com/apis/credentials (обычный API-ключ, не OAuth).
   - `YOUTUBE_PLAYER_CLIENT` — если mpv при заказе падает с ошибкой вида
     `Sign in to confirm you're not a bot` или `The page needs to be
     reloaded` (это про локальное воспроизведение через mpv/yt-dlp, никак
     не связано с `YOUTUBE_API_KEY` выше) — значение по умолчанию уже
     пытается это обходить, но раз YouTube меняет правила постоянно, могут
     понадобиться `YOUTUBE_COOKIES_FROM_BROWSER`/`YTDLP_PATH` из
     `.env.example` — там же подробный разбор обеих ошибок.
   - `MPV_VOLUME` (по умолчанию `50`) — громкость mpv при старте YouTube-заказа
     (0-100), чтобы не оглушало после Spotify.

   **Заказ музыки — Spotify** (необязательно — см. "Необязательные интеграции" выше)
   - `SPOTIFY_CLIENT_ID` / `SPOTIFY_CLIENT_SECRET` — приложение на
     https://developer.spotify.com/dashboard. В Redirect URIs добавь
     `http://127.0.0.1:8888/callback`. Важно: именно `127.0.0.1`, а не
     `localhost` — у Spotify для http принимается только IP-адрес
     loopback (правило обратное Twitch-у выше).
   - `SPOTIFY_DEFAULT_PLAYLIST_URI` — дефолтный плейлист. Проще всего:
     в Spotify у плейлиста `...` → Share → Copy link to playlist — обычную
     ссылку вида `https://open.spotify.com/playlist/<id>?si=...` можно
     вставить как есть, приложение само приведёт её к нужному виду
     (см. `src/music/spotifyPlaylistUri.ts`). "Copy Spotify URI" тоже
     подойдёт, если она у тебя есть — но эта опция то пропадает, то
     появляется в разных версиях Spotify, поэтому полагаться на неё не стоит.
     Вместо ссылки можно указать `TOP` — тогда дефолтными треками станет
     микс твоих топ-треков Spotify (`/me/top/tracks`): поровну из топов за
     год, полгода и месяц (`long_term`/`medium_term`/`short_term`), без
     дублей, всегда перемешанный (см. `src/music/spotifyTopMix.ts`).
     Daylist и Daily Mix так взять нельзя: Spotify не отдаёт алгоритмические
     плейлисты приложениям в режиме разработки. Для `TOP` токену нужно право
     `user-top-read` — после обновления заново запусти `npm run auth:spotify`.
   - Если Spotify настроен, `!sr` дополнительно принимает текстовый запрос
     вместо ссылки (например `!sr Rick Astley - Never Gonna Give You Up`) —
     заказывается первый результат поиска в Spotify по этому тексту
     (см. "Как работает заказ музыки" ниже).

4. Пройди одноразовую авторизацию (открывает ссылку — нужно один раз
   разрешить доступ в браузере, токены с refresh сохранятся на диск). На
   Windows — `setup-1-twitch-auth.bat` и `setup-2-spotify-auth.bat` (см.
   выше), либо в терминале:
   ```bash
   npm run auth:twitch     # чат + проверка фолловеров — всегда нужно
   npm run auth:spotify    # управление воспроизведением — только если настроил Spotify (см. выше)
   npm run auth:twitch-points  # награды за баллы канала — только для MUSIC_REQUEST_MODE=points (см. ниже)
   ```

5. Если настроил Spotify: открой его (desktop/mobile/web) на устройстве, где
   должна играть музыка на стриме, и узнай его точное имя — на Windows
   `setup-3-spotify-devices.bat`, либо в терминале:
   ```bash
   npm run devices:spotify
   ```
   Впиши это имя в `SPOTIFY_DEVICE_NAME` в `.env`. Это не строго
   обязательно, но без этого Spotify Web API требует, чтобы у аккаунта
   уже было "активное устройство" — иначе запуск плейлиста падает с
   `HTTP 404` ("нет активного устройства"), даже если Spotify открыт.
   С `SPOTIFY_DEVICE_NAME` приложение явно указывает Spotify, где играть,
   и это работает, даже если на устройстве сейчас ничего не играет —
   достаточно, чтобы Spotify был просто запущен.

## Запуск

На Windows проще всего двойным кликом по `start.bat` (см. "Windows: запуск
без консоли" выше) — или по `start-paused.bat`, если нужно сразу поднять
приложение с приостановленными заказами музыки (тот же `start.bat`, но с
флагом `-s`, см. "Приостановка заказов" ниже). В терминале (любая ОС):

```bash
npm start        # обычный запуск
npm run dev       # с автоперезапуском при изменении файлов (node --watch)
npm start -- -s   # запуск сразу с приостановленными заказами музыки (см. ниже)
```

### Как работает заказ музыки

1. Зритель пишет в чат `!sr <ссылка или название трека>`.
2. Проверяется, что он фолловер канала от `MUSIC_MIN_FOLLOWER_DAYS` дней —
   если нет, бот отвечает и на этом всё. **Исключение — сам broadcaster**:
   Twitch не позволяет зафолловить собственный канал, поэтому для аккаунта
   стримера эта проверка пропускается вообще (определяется по бейджу
   `broadcaster` в чате, а не по имени пользователя).
3. Ссылка должна быть на YouTube, Spotify-трек или трек Яндекс Музыки
   (последняя — только если задан `YANDEX_MUSIC_TOKEN`). Если это не похоже на
   ссылку вообще и Spotify настроен — приложение ищет трек в Spotify по
   тексту (например `!sr Rick Astley - Never Gonna Give You Up`) и
   заказывает первый результат поиска — то же самое, что показал бы поиск в
   самом приложении Spotify первым пунктом. Если результатов вообще нет —
   "ссылка невалидная". Если Spotify не настроен — принимаются только
   ссылки на YouTube.
4. Для YouTube дополнительно проверяется длительность (по умолчанию не
   больше 10 минут, `YOUTUBE_MAX_DURATION_SEC`).
5. Валидный заказ кладётся в конец очереди (SQLite), бот подтверждает в
   чат: `трек добавлен в очередь: "..." (позиция N)`. Для YouTube это просто
   название видео, для Spotify — "Исполнитель - Название" (у Spotify-трека
   почти всегда есть чёткое поле исполнителя, а без него не всегда понятно,
   о каком именно треке речь — мало ли одноимённых каверов и ремиксов).
6. Воспроизведение устроено как две очереди в базе SQLite и один цикл:
   - `song_requests` — заказы зрителей;
   - `default_tracks` — треки дефолтного плейлиста (`SPOTIFY_DEFAULT_PLAYLIST_URI`
     или `YANDEX_DEFAULT_PLAYLIST_URL`). При старте приложения таблица
     очищается и заполняется всеми треками плейлиста (по умолчанию
     вперемешку, `DEFAULT_PLAYLIST_SHUFFLE=false` — по порядку). Когда
     треки закончились, плейлист загружается заново. Моя волна
     (`YANDEX_DEFAULT_PLAYLIST_URL=WAVE`) вместо этого дописывает в таблицу
     порцию за порцией.

   Цикл простой: есть заказ — играет заказ; нет — играет первый трек из
   `default_tracks`. Текущий трек всегда доигрывает до конца, поэтому заказ,
   пришедший во время дефолтного трека, играет сразу после него. Сыгранный
   заказ помечается `done`, сыгранный дефолтный трек удаляется из таблицы.
   Если дефолтный плейлист не задан или не загрузился, между заказами тишина
   (загрузка повторяется раз в минуту).
7. Заказы играют строго по очереди (FIFO, без приоритетов). Треки Spotify
   играет Spotify (через Spotify Connect), YouTube и Яндекс Музыку — mpv (со
   стартовой громкостью `MPV_VOLUME`, по умолчанию 50%). Перед треком mpv и
   когда играть нечего Spotify ставится на паузу — иначе он продолжил бы
   играть что-то своё поверх.
8. Трек, который не удалось сыграть (нет сети, трек недоступен и т.п.),
   пропускается, и цикл идёт дальше.

### Как работает скип (`!skip`)

Работает и во время заказа, и во время дефолтного плейлиста (когда
очередь заказов пуста) — логика одинаковая, с одним отличием (см. ниже про
мгновенный скип заказчиком).

- Если команду пишет сам стример или модератор канала — текущий трек
  скипается сразу, без голосования (проще всего сообразить, зачем это может понадобиться —
  YouTube-заказ иначе не переключить, в отличие от Spotify). Исключение:
  модератор скипает сразу (и заказ, и трек дефолтного плейлиста), только если
  `MUSIC_MODERATOR_SKIP_REQUESTS=true` (по умолчанию `false`) — иначе его
  `!skip` считается обычным голосом (или мгновенным скипом, если это его собственный заказ и это
  разрешено заказчикам, см. ниже).
- Если команду пишет тот же зритель, который этот трек и заказал, и
  `MUSIC_REQUESTER_SKIP_REQUESTS=true` (по умолчанию `false`) — тоже
  скипается сразу, без голосования (это его собственный заказ, разумно, что
  он может передумать без порога). При `false` его `!skip` — обычный голос. Право на мгновенный скип действует
  только для трека, который сейчас реально играет — если зритель заказал
  что-то в очередь, но играет ещё не его заказ, обычный `!skip` от него
  идёт в общее голосование, как от любого другого зрителя. У треков
  дефолтного плейлиста заказчика нет — эта льгота на них не распространяется.
- Если пишет кто-то ещё — это голос. Трек скипается, когда голосов наберётся
  не меньше `MUSIC_SKIP_THRESHOLD_PERCENT` процентов (по умолчанию 30%,
  округление вверх) от числа **зрителей стрима** (`viewer_count` из Twitch
  Get Streams). Число зрителей запрашивается один раз на трек — при первом
  голосе — и порог до конца трека не меняется. Если стрим оффлайн,
  достаточно одного голоса.
- Голоса за конкретный трек сбрасываются, как только начинает играть
  следующий трек — заказ или трек дефолтного плейлиста.
- Если играть вообще нечего (дефолтный плейлист не задан или не загрузился,
  а в очереди нет заказов) — бот ответит соответствующим сообщением, ничего
  не скипая.
- Для YouTube-заказа скип останавливает и yt-dlp, и mpv (см. "Как играют
  YouTube-заказы" выше — это два отдельных процесса, соединённых пайпом, а
  не один запускает другого). На Windows каждый из них останавливается через
  `taskkill /T /F` (а не обычный `child.kill()`) — Node.js на Windows лишь
  эмулирует POSIX-сигналы, и обычный `kill()` не гарантирует остановку всего
  дерева процессов — из-за этого раньше "скипнутый" mpv мог не закрыться до
  конца и продолжить играть параллельно со следующим треком. `/T` останавливает
  всё дерево процессов, `/F` — принудительно.
  Для Spotify-трека (и заказа, и дефолтного) приложение не прерывает сам
  трек через Spotify API — досрочно завершается ожидание его конца, и
  оркестратор сразу запускает следующий трек (или ставит Spotify на паузу,
  если дальше трек mpv или играть нечего). Скипнутый дефолтный трек
  считается сыгранным и удаляется из таблицы.

### Приостановка заказов (`!pr` / `!rr`)

Доступно только стримеру и модераторам.

- `!pr` — приостанавливает приём новых заказов (зрителям бот отвечает, что
  заказы сейчас недоступны) и останавливает дефолтный плейлист, если он в
  этот момент играет. Остановленный трек остаётся в таблице и после `!rr`
  начнётся сначала. Уже принятые в очередь заказы никуда не деваются и
  доигрывают как обычно — команда останавливает именно приём новых.
- `!rr` — снова разрешает заказы и сразу продолжает дефолтный плейлист.
- Флаг `-s` (или `--pause-requests`) при запуске приложения — то же самое, что
  сразу набрать `!pr` после старта, но без похода в чат (например, если перед
  стримом заведомо нужна техническая пауза). Включить заказы обратно можно
  командой `!rr` в чате. На Windows для этого есть отдельный `start-paused.bat`
  рядом с обычным `start.bat` — двойной клик по нему запускает приложение
  сразу с этим флагом, ничего вручную вписывать не нужно.

### Заказ за баллы канала (`MUSIC_REQUEST_MODE=points`)

Отдельный режим вместо заказа командой: одновременно работает только один
из двух. Переключается в `.env`, вступает в силу после перезапуска.

- Зритель активирует награду (по умолчанию "Заказ музыки" за 500 баллов) и
  пишет в ней ссылку или название трека — то же, что писал бы после `!sr`.
- Правила те же, что у команды: пауза заказов (`!pr`), валидация
  ссылки/поиск в Spotify, лимит длительности YouTube. Исключение — фолловинг:
  за баллы может заказывать любой зритель, `MUSIC_MIN_FOLLOWER_DAYS` здесь
  не проверяется.
- Трек встал в очередь — награда ждёт ("в ожидании"), пока трек реально не
  зазвучит, и тогда отмечается выполненной. Трек не запустился (yt-dlp не
  скачал, Spotify не заиграл, скипнули до начала) — награда отклоняется, и
  Twitch возвращает баллы; бот пишет в чат "не получилось включить …".
  Не встал в очередь по любой причине (не прошёл правила, заказы на паузе,
  непредвиденная ошибка) — награда отклоняется сразу, бот пишет в чат
  причину отказа — те же сообщения, что и у `!sr`.
- `!sr` в этом режиме ничего не заказывает — только подсказывает название награды.
- Privilege-режим (`MUSIC_PRIVILEGE_MODE=true`, по умолчанию выключен):
  заказы стримера, модераторов и VIP проходят по тем же правилам и встают
  в очередь, но награда отклоняется — баллы возвращаются. Ответ в чате
  обычный. Для остальных зрителей ничего не меняется.
  Роль проверяется через Twitch API токеном стримера; если проверка не
  удалась — заказ считается платным. Токену нужны скоупы `moderation:read`
  и `channel:read:vips`: если `auth:twitch-points` проходили до появления
  этого режима — пройди её ещё раз, иначе приложение предупредит при старте
  и будет работать без привилегий.

Настройка:

1. Баллы канала есть только у компаньонов и партнёров Twitch.
2. `MUSIC_REQUEST_MODE=points` в `.env`, при желании — `MUSIC_REWARD_TITLE`,
   `MUSIC_REWARD_COST`, `MUSIC_REWARD_PROMPT`. Они нужны только для
   создания награды при первом запуске (см. пункт 4).
3. Один раз `npm run auth:twitch-points` (или `setup-4-twitch-points-auth.bat`),
   **залогинившись в браузере аккаунтом канала**. Twitch даёт управлять
   наградами только самому стримеру — даже модератору нельзя, поэтому
   это отдельный токен (`TWITCH_BROADCASTER_TOKEN_FILE`), независимый от
   токена бота. Если бот — это ты сам, авторизоваться всё равно нужно и
   здесь, и в `auth:twitch`. Если перепутал аккаунт — приложение при старте
   скажет об этом явно.
4. **Не создавай награду вручную в панели Twitch** — приложение создаёт её
   само при первом запуске. Twitch позволяет выполнять/отклонять только
   награды, созданные тем же приложением (тем же `TWITCH_CLIENT_ID`); если
   награда с тем же названием уже создана вручную — приложение сообщит об
   этом при старте (удали её — приложение создаст свою с тем же
   названием — или смени `MUSIC_REWARD_TITLE`).
5. Дальше награду настраиваешь в панели Twitch как обычно: название, цена,
   подсказка, иконка и т.д. Приложение запоминает её id (в SQLite, рядом с
   очередью заказов) и находит её по нему, даже если её переименовать, а
   эти поля не перезаписывает. При каждом запуске оно следит только за
   тем, без чего режим не работает: награда включена, не на паузе, требует
   текст от зрителя и не помечает активации выполненными автоматически
   (иначе вернуть баллы при отказе было бы уже нельзя). Если награду
   удалить — при следующем запуске приложение создаст новую из `.env`.

Что происходит с наградой вне работы приложения:

- При выходе (закрытие окна через Ctrl+C) награда ставится на паузу —
  видна зрителям, но активировать её нельзя, пока заказы некому обработать.
  При следующем запуске пауза снимается.
- Если приложение упало и зрители успели активировать награду, пока оно не
  работало — при следующем запуске такие активации отклоняются с возвратом
  баллов (задним числом их уже не обработать). Активации заказов, которые
  стоят в очереди и ещё не играли, не трогаются — их выполнят или отклонят,
  когда до них дойдёт очередь.
- При запуске в режиме `command` награда, оставшаяся с режима баллов,
  выключается совсем (если есть токен стримера) — чтобы никто не тратил
  баллы впустую.

### Про звук YouTube-заказов в OBS

YouTube-заказы играют через отдельный процесс mpv — сам код не может
"подключить" его звук к OBS напрямую, это обычная задача роутинга звука на
уровне ОС/OBS, не специфичная для этого приложения. Но приложение умеет
направить звук mpv на конкретное аудио-устройство через `MPV_AUDIO_DEVICE`
в `.env` (см. `.env.example`) — этого вместе с виртуальным аудио-кабелем
достаточно, чтобы в OBS ловить звук именно YouTube-заказов отдельно от
остального. Подробно, по шагам (Windows, с [VB-CABLE](https://vb-audio.com/Cable/)):

1. **Поставь VB-CABLE**, если ещё не сделал (бесплатно, ссылка выше —
   раздел Donationware, скачать архив, распаковать, запустить
   `VBCABLE_Setup_x64.exe` от имени администратора, перезагрузить Windows
   после установки — без перезагрузки новое устройство иногда не подхватывается).
   VB-CABLE добавляет в Windows пару виртуальных устройств: **CABLE Input**
   (устройство "воспроизведения" — на него приложения ОТПРАВЛЯЮТ звук) и
   **CABLE Output** (устройство "записи" — с него можно этот же звук
   ЗАБРАТЬ, например в OBS). По сути это провод между двумя розетками.

2. **Узнай точное имя устройства для mpv.** Открой командную строку
   (Win+R → `cmd` → Enter) и выполни:
   ```
   mpv --audio-device=help
   ```
   Если команда не находится — впиши в неё полный путь к `mpv.exe` вместо
   `mpv`. В выводе найди строку, где в скобках упоминается `CABLE Input`,
   например:
   ```
   'wasapi/{05a4a939-...-...-...-............}' (CABLE Input (VB-Audio Virtual Cable))
   ```
   Тебе нужна именно часть в одинарных кавычках —
   `wasapi/{05a4a939-...}`.

3. **Впиши это значение в `.env`**:
   ```
   MPV_AUDIO_DEVICE=wasapi/{05a4a939-...-...-...-............}
   ```
   (без одинарных кавычек — просто сам текст). Перезапусти приложение
   (`start.bat` — см. "Windows: запуск без консоли"), чтобы .env
   перечитался.

4. **Проверь заказом.** Закажи что-нибудь через `!sr <ссылка на YouTube>` —
   звук из колонок/наушников напрямую слышно быть не должно (он теперь
   уходит только в CABLE Input) — это ожидаемо, а не баг, звук просто ждёт
   в "проводе" на выходе CABLE Output.

5. **В OBS добавь источник звука.** Источники → `+` → **"Захват вывода
   аудио" (Audio Output Capture)** → в качестве устройства выбери
   **CABLE Output**. Теперь в сцене есть отдельная звуковая дорожка именно
   YouTube-заказов — её видно и регулируется отдельно в микшере аудио OBS,
   независимо от остального звука.

6. **Чтобы слышать заказы самому (мониторинг), а не только зрителям** —
   иначе ты не будешь слышать, что играет:
   - В OBS: правой кнопкой по добавленному источнику `CABLE Output` →
     **Свойства аудио** (Advanced Audio Properties) → **Аудио мониторинг**
     (Audio Monitoring) → выбери **"Мониторинг и вывод"** (Monitor and Output).
   - Один раз в целом по OBS: Настройки → Аудио → Дополнительно →
     **Устройство мониторинга** (Monitoring Device) — укажи свои
     наушники/колонки. После этого звук из CABLE Output будет идти и в
     стрим, и тебе в наушники через сам OBS — без обратной петли и
     задержки, в отличие от варианта "Прослушивать это устройство" в
     настройках звука Windows (тоже сработает, но добавляет лишнюю
     задержку и звук не пройдёт через микшер OBS).

Поскольку направляется звук именно mpv (через `MPV_AUDIO_DEVICE`), а не всё
устройство вывода Windows целиком — Spotify, звук Discord и всё остальное
как играло в обычные колонки/наушники, так и продолжает — трогать
"устройство по умолчанию" в Windows не нужно вообще.

На macOS аналогичную роль играет [BlackHole](https://github.com/ExistentialAudio/BlackHole)
или [Loopback](https://rogueamoeba.com/loopback/) — принцип тот же: узнать
точное имя устройства (`mpv --audio-device=help` работает и там), вписать
его в `MPV_AUDIO_DEVICE`, дальше OBS захватывает его так же через Audio
Output Capture.

## Оверлей для OBS ("сейчас играет")

Приложение само отдаёт плашку с текущим треком: обложка, название,
исполнитель, кто заказал (только у заказов), время и полоса прогресса.
Цвета плашки подбираются под обложку.

В OBS: Источники → `+` → **"Браузер"**, адрес `http://localhost:8890/overlay`,
ширина `440`, высота `160`. Фон у страницы прозрачный. Пока ничего не играет
(или заказы на паузе `!pr`), плашка спрятана.

Откуда берутся данные:
- **Spotify** — название и исполнитель из Spotify, обложка альбома через
  Spotify API, прогресс и пауза — у самого Spotify (раз в секунду).
- **YouTube** — превью видео (`i.ytimg.com`, без запросов к YouTube API и
  без расхода квоты). Название видео разбирается на исполнителя и трек по
  разделителю `Исполнитель - Название`, приписки вроде `(Official Video)`,
  `[4K Remaster]`, `(Lyrics)`, `(Официальный клип)` вырезаются (см.
  `src/overlay/trackDisplay.ts`). Прогресс считается с момента, когда mpv
  реально начал играть звук.
- **Яндекс Музыка** — обложка трека из её API.

Параметры в адресе (необязательно): `?scale=1.5` — увеличить плашку,
`?requester=0` — не показывать, кто заказал, `?autohide=10` — показывать
плашку только 10 секунд после смены трека. Можно сочетать:
`http://localhost:8890/overlay?scale=1.5&autohide=10`.

Порт меняется через `OVERLAY_PORT` в `.env` (`0` или `off` — выключить
оверлей). Сервер слушает только `127.0.0.1` — снаружи компьютера он не виден.

## Тесты

```bash

```

Юнит-тестами покрыто всё, что не требует реальной сети/аккаунтов: разбор
ссылок (YouTube/Spotify/невалидные), разбор Twitch IRC-протокола, разбор
длительности YouTube, FIFO-очередь в SQLite, обработчик заказа целиком
(follower-check → валидация → постановка в очередь → ответ в чат — на
подменённом `fetch`), state machine переключения default/очередь
(на фейковых Spotify/YouTube-плеерах), обёртка над процессом-плеером
(реальный `node`-процесс вместо mpv), заказ за баллы канала (выполнение/

Реальные сетевые вызовы (Twitch IRC и EventSub WebSocket, живые Spotify/YouTube API, сам mpv) тестами не покрыты — их
можно проверить только на твоей машине с реальными токенами и `mpv`/`yt-dlp`
в PATH.

## Известные ограничения / осознанные решения

- YouTube-заказы играют через mpv — у него есть настоящий сигнал о конце
  трека (mpv-процесс сам завершается), поллинг тут не нужен вообще.
- У Spotify Web API нет событий "трек закончился", поэтому пока играет
  Spotify-трек, его состояние опрашивается раз в `SPOTIFY_POLL_INTERVAL_MS`
  (см. `spotifyTrackPlayer.ts`). Правила:
  - трек считается начавшимся, только когда Spotify подтвердил, что играет
    именно он. Если заиграл чужой трек (застрявший в очереди Spotify —
    удалить из очереди через API нельзя), приложение жмёт "следующий", пока
    не дойдёт до нужного. Если ничего не играет — повторяет запуск. Не
    заиграл совсем — трек пропускается;
  - трек считается закончившимся, только когда Spotify ушёл на другой трек
    или остановился в самом конце. Ручная пауза посреди трека концом не
    считается, единичные сбои сети тоже (5 подряд — трек пропускается);
  - за 15 секунд до конца Spotify-трека следующий трек, если он тоже из
    Spotify, заранее ставится в очередь Spotify, и Spotify переключается на
    него сам — без паузы и без чужого трека между ними. Выбор следующего
    трека при этом фиксируется: заказ, пришедший позже, сыграет через один
    трек (удалить трек из очереди Spotify через API нельзя);
  - если следующий трек не из Spotify (YouTube, Яндекс) или играть нечего,
    за 2 секунды до конца опрос прекращается, трек доигрывается по часам, и
    за секунду до конца Spotify ставится на паузу — последняя секунда
    обрезается, зато автовоспроизведение Spotify не успевает прорваться.
- `playTrackUri` реализован через `POST /me/player/queue` + `POST
  /me/player/next`, а не через прямой `PUT /me/player/play` с `{"uris": [...]}`:
  на практике прямой запрос принимался Spotify с HTTP 204, но ничего не
  запускал.
- Дефолтный плейлист Spotify читается через `GET /playlists/{id}/items`
  (старый `/tracks` Spotify закрыл). Приложениям Spotify в режиме разработки
  доступны только плейлисты из медиатеки пользователя: чужой плейлист нужно
  сначала добавить в медиатеку, иначе Spotify отвечает 403.
- `device_id` (когда задан `SPOTIFY_DEVICE_NAME`) резолвится через отдельный
  `GET /me/player/devices` и кэшируется на 10 минут, чтобы не делать лишний
  запрос на каждое действие с плеером. Первый же неудачный запрос к
  устройству сбрасывает кэш.
- Если `TWITCH_CHAT_BOT_USERNAME` — не сам broadcaster, этот аккаунт должен
  быть модератором канала, иначе Twitch не даст скоуп `moderator:read:followers`.
- `node:sqlite` и `WebSocket` в Node помечены experimental/новыми — печатают
  предупреждение при старте, это безопасно игнорировать.
- Скачивание аудио с YouTube через yt-dlp формально в серой зоне ToS
  YouTube — это личный инструмент для собственного стрима, но стоит иметь в виду.
- Порог голосования за скип (`MUSIC_SKIP_THRESHOLD_PERCENT`) считается от
  `viewer_count` из Twitch Get Streams, а Twitch обновляет это число с
  задержкой в пару минут — в начале стрима порог может быть занижен.
- Звук YouTube-заказов (через mpv) не подключается к OBS автоматически —
  это отдельная задача роутинга аудио на уровне ОС, см. "Про звук
  YouTube-заказов в OBS" выше.
